# Snapshot capture and loading cancellation

- Problem: capture already accepts an engine cancellation flag, but History never receives its operation ID. Loading discards the flag and uses the uncancellable Store entry point. Users cannot cancel either long operation from History.
- Change: send the owning operation ID through a native channel after validation. History exposes one Cancel control only during native capture/loading. Operation generations cancel late acknowledgements after unmount and prevent stale replies from changing a new action.
- Core: require an explicit cancellation flag on Store::load and migrate every caller. Check before opening the transaction, between rows and before returning. Capture retains its existing transactional pre-commit cancellation. Cancellation returns no published index and retains the previous analysis.
- Result: native capture returns an optional saved ID and loading an optional publication ID. None means cancellation before completion. A successful committed capture remains success even if cancellation arrives afterward. Hide Cancel before frontend refresh/adoption starts.
- Verification: extend the existing snapshot case with cancelled loading, cancelled capture and snapshot preservation. Keep eight declared tests. Run the production-mode source gate, rebuild with production enabled, open the verified image and refresh the installer. No subagents, Computer Use or deferred UAC.

Result: channel ownership and Cancel are connected for capture/loading. Core loading requires an explicit flag, and all callers are migrated. Native publication holds the cancellation mutex and is directly covered by the existing command case. The restored code passes all six production source checks with eight declared tests. The ignored-flag mutation fails the retained snapshot case as expected. Native interaction, focus and cancellation latency remain manual acceptance, including the documented in-flight SQLite/mutex limit.
