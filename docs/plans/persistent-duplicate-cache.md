# Persistent duplicate hash cache

1. Ground. Duplicate sampling and full hashing already validate an opened file identity, length, modification time and native change time. HashCache keeps at most 250,000 identities but disappears on exit. The snapshot store already owns the local WAL database and its schema migration. The native operation gate serializes duplicate analysis with scan and snapshot mutation.
2. Sketch. Add a bounded hash table in snapshot schema 5, storing fixed-size identity, metadata and digest fields. Load it only when duplicate analysis starts, then transactionally replace it with the updated bounded cache. The file must still be opened and match the complete stamp before a hit is accepted. Cleanup continues fresh content verification. No startup cache load or per-file SQLite transaction.
3. Decision. Reuse the existing Store instead of a second database and connection lifecycle. Replace the native in-memory cache owner with a local cache per duplicate operation. A cache read/write failure is reported as an analysis issue while ordinary hashing remains available. Invalid cache rows are ignored, and no row may bypass file validation. No paths or file content are stored. Pre-epoch timestamps are omitted rather than rounded.
4. Implement. Add migration and bounded codecs, store load/save methods, native lazy load/save and retained integration-case coverage. Verify cold hashing, reopened zero-content-read reuse, same-size edited-file invalidation, malformed-row fallback and schema-4 migration without adding declared tests.
5. Verify and scrap. Run counterexample and full source gate, rebuild and open the native app, retain one preview, refresh the installer if the implementation is accepted. Remove the old Engine hash-cache field and the persistence shortcut comment in the same change. No subagents, Computer Use or deferred UAC.

Result: the cache is implemented and the old Engine-owned cache field and shortcut are removed. The retained real-file case passes migration, reopened reuse, malformed-row fallback, same-size edited-file invalidation, cancellation rollback and explicit clearing without snapshot loss. Omitting change-time matching produces a false duplicate and fails the case. All six source stages pass with eight declared tests. The release executable builds and opens a responding native window. The offline package has been refreshed and statically verified from that same executable; native duplicate interaction and large-cache performance remain manual or unmeasured.
