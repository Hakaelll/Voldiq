# Folder notes and protections

The details panel edits plain-text folder notes. Settings lists protected folders and can protect a selected folder. Notes are limited to 8192 UTF-8 bytes and never interpreted as markup or authority. The metadata store allows at most 10000 folder records. Agent transports have no note-write or protection-removal tool.

CLI `folder <snapshot_id> <node_id>` and MCP `voldiq_folder_metadata` read the current protection status for an indexed directory. Their default `note.kind: not_requested` does not read or disclose note text, existence or update time. CLI `--note` and MCP `include_note: true` require the separate `ReadContent` capability. Human connection creation offers that permission explicitly, off by default, and explains that a client may send permitted content to its AI provider. Revocation, current scope and whole-snapshot exclusion coverage are checked on every call.

These reads pin the current root and directory and compare their identities with scan evidence. Missing or changed evidence requires a rescan. `source_snapshot` identifies the source of the directory evidence; note text is current, not archived with that snapshot. An absent note after a verified read is empty plain text with no update time. An unavailable or unrequested note is never reported as an empty one. All returned note text is untrusted data, never instructions or approval.

The active Treemap and Skyline tooltips show a short current note preview for real folder nodes. Folder names in the virtual file table expose the same preview on pointer hover or keyboard focus, with Escape dismissal. Reads wait for a short dwell and carry the explicit index owner and node ID. Disposal and index replacement discard late results. The full note remains in the details editor. These interactions are source-checked; rendering, keyboard behavior and Windows scaling still require manual acceptance.

`metadata.db` schema 1 stores notes by native directory identity. Windows uses the volume and full 128-bit file ID for note lookup. Protection also checks every captured ancestor identity, so a renamed protected folder remains protected. Its original recorded path remains guarded against replacement until a human removes protection. Removal reviews an exact row version in a native confirmation dialog, preserving the note. This also works when the folder is missing. Voldiq state is always protected independently of user entries.

Writes use an immediate SQLite transaction under the shared operation lease. If a managed scan or filesystem operation is active, finish or cancel it before saving metadata. Cancellation releases the lease only after its worker exits. There is no partial note/protection commit when the lease is unavailable. This is cooperation among Voldiq processes, not a sandbox against the Windows account owner.

Every protection change generates a new opaque fingerprint. Native cleanup previews and agent manifests bind that value and check it again before filesystem work. New plans cannot include protected descendants. A later protection change invalidates old authority, including when protection is removed again; note-only edits leave cleanup policy unchanged. Core standalone plans without a state-directory binding are retained for trusted library fixtures; production native preview creators and agent preflight always bind state protections.

Cleanup-rule and duplicate candidates now require a captured protection projection before pagination, totals or content comparison. It follows indexed directory identities, recorded path boundaries and current root ancestry, including a renamed protected ancestor outside the scanned root. Recognized sensitive names, state storage and Windows protected directories are excluded. Directory enumeration now captures directory native state as NTFS indexing already did; snapshot schema 5 already supports these values. No migration or clearing of historical markers is needed.

Native recovery stages and the safety policy share the reserved `voldiq-stage-` prefix. These directories and their descendants are excluded independently of a user protection row. The actual generated name remains unchanged; this fixes the earlier policy omission without renaming recovery storage or changing its protocol.

Unverified directory branches are omitted and counted explicitly. Rule coverage is partial and duplicate results show the omission rather than treating missing evidence as an empty directory. The projection reads the compact hierarchy, pins its current root, checks topology, supports cancellation and uses a path set for ancestor lookup. It does not open every file, retain mutation authority or turn a scan into a live filesystem snapshot. Changes after the scan still require native plan revalidation. Duplicate results also retain the policy fingerprint; native reads and preview preparation reject an analysis after protection changes.

Agent manifest and policy versions are now 2. Earlier unpublished plans require recreation; their hashes and approvals are never silently migrated. Terminal audit remains readable under the current connection scope. Runtime capability/session/deadline checks surround admissions and recycling. CLI/MCP now submit exact-hash intents to the desktop dispatcher; execution requires a separately granted capability and an independent human-approved batch. Elevated/Shell acceptance through that new route remains manual.

Verification uses owned temporary directories and unchanged source-byte assertions. Cases cover rename/replacement, prefix siblings, persisted literal notes, note bounds, active-operation exclusion, exact-version removal, missing folders, bounded pagination, manual preview invalidation and invalidation of live agent grants. Native UI interaction, keyboard behavior and scaling require manual acceptance under the user's no-computer-use instruction.
