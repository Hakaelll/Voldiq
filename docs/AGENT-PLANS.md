# Agent plan boundary

The core stores exact recycling manifests. CLI/MCP prepare and inspect them; the desktop owns separate human review and live grants. Approved tickets now support exact native preflight and journal association. Execution dispatch is pending. No agent file mutation endpoint is enabled.

A manifest identifies its connection, Windows user, source snapshot, root identity, selected file identities, bytes, timestamps, risk, action and expiry. Byte quantities and native identities are strings, preserving exact values in JavaScript clients. Recycling reports zero immediate freed bytes; potential allocation recovery is a separate value and excludes multiply linked files.

The public manifest includes a BLAKE3 hash of private native evidence. That evidence records every parent identity and exact exclusions without exposing ancestor identities or excluded path names in the public response. The manifest itself has a separate BLAKE3 hash. These hashes detect changed evidence; the local database and audit are not claimed to resist the Windows account owner editing them.

Policies are rechecked on every call. An opaque binding includes the current credential digest and complete policy. Rotation, revocation and changed policy invalidate prior authority. Registry, plan store and approver must belong to the same pinned state directory. Known credential locations, Git internals, virtual disks, protected system directories and the state directory are blocked. User-defined folder protections apply to descendants and follow native identities across renames. Manifest schema and policy version 2 bind an opaque protection fingerprint; earlier manifests require a new plan. A protection change invalidates existing previews and pending approvals even if protection is later removed. Editing only a note does not change that fingerprint.

Plans expire after 15 minutes. A human approval lasts at most two minutes, bounded by the plan expiry. The opaque ticket retains that deadline; entering `executing` does not extend it, and delayed preflight is denied. Human approval requires an exclusive OS lease and an in-memory grant bound to the manifest hash, connection and policy. An `approved` SQLite row, even with the current issuer identifier, cannot produce an execution ticket. The agent transport has no approval endpoint.

The lifecycle is `draft`, `awaiting_approval`, `approved`, `executing`, then a terminal result. Rejection, expiry and changed material evidence are terminal. Transactions allow one opaque execution ticket; concurrent or repeated calls report the existing operation. Finishing requires that ticket and its private nonce. Starting a new human session discards old grants. Explicit recovery returns old approvals to review and marks abandoned execution `failed` with `recovery_required`, without repeating uncertain I/O.

The store does not execute files. SQLite requests/status coordinate the clients and desktop; they never prove approval. The desktop facade owns the only live human grants, uses current connection policy without credentials in IPC, and invalidates the session when the native window is destroyed.

Plan-store schema 2 adds exact-hash execution requests and cooperative cancellation intents. Migration from schema 1 preserves manifests, hashes and audit sequences. Older binaries that only understand schema 1 cannot reopen schema 2. This changes neither manifest version 2 nor approval authority. The queue is bounded by the existing 10000-plan retention limit and human discovery returns at most 100 requests at a time.

Request creation requires the owning connection's current `ExecuteApproved` capability, current scope, unchanged material evidence and an unexpired approved plan. Repeated requests for that session preserve the original request time and emit one audit event. Discovery is limited to the current human session and omits cancelled, expired or already executing entries. A new desktop session requires renewed approval and a fresh explicit execution request. Even a forged approved row and queued request cannot consume a missing in-memory human grant.

Cancellation before execution makes the plan terminal, blocking its live grant. During execution it records a stop request and leaves the plan `executing` until the worker records its actual result. Reading or changing an intent rechecks owner, hash and current capability; an intent from an older approval session is not returned as the current request. These core APIs do not launch a helper or modify source files. CLI/MCP execution remains disabled until desktop dispatch, operation-lease retention and runtime checks use them.

The shared recycling executor now requires the complete selection to pass preparation before launching its elevated helper. Its lower-level admission method enforces the same gate. A changed or inaccessible entry aborts all prepared sources; runtime failures still produce explicit per-file outcomes. Native verification also compares allocation and hard-link count. The desktop displays a batch preflight error without implying that the valid subset ran.

`Store::prepare_recycling` consumes the opaque approved ticket, rechecks current authority, policy, manifest and disk evidence, then constructs the exact internal plan. It requires a current-session execution request and a worker context borrowing the shared operation lease, cancellation token and STA apartment. The non-serializable prepared object holds source and ancestor handles and retains those worker borrows until cancellation or execution finishes. It cannot be expanded with additional paths or used through an agent tool. A failed preparation cancels owned stages and terminates the plan. Closing a prepared source handle or restarting never repeats uncertain work automatically.

Prepared execution now checks current capability/credential/policy, live human session, Windows user, exact manifest/nonce/state, approval deadline, protection fingerprint and current-session request before helper launch, before each admission and before recycling. Deadline and session checks run again after database reads. Complete material evidence is validated in preflight; the repeated authority query is bounded and does not parse the entire manifest per file. Native source/content/destination checks remain in place. A final authority check runs after content verification and Shell binding, before recycling intent and the Shell operation.

Withdrawal stops further admissions or recycling, closes the helper and uses the existing guarded return path for staged originals when possible. Unknown results remain unknown. The bounded plan summary includes node outcomes, confirmed admissions, unknown counts and journal/helper/cleanup failure flags. It omits raw paths, bin locators and execution nonces. Recycling reports zero immediate freed bytes. Partial recycling is never labelled fully cancelled; failed journal or cleanup reconciliation remains failed even if cancellation was requested.

Cleanup-journal schema 5 associates each agent relocation with its manifest, connection and execution nonce in the same transaction as preparation, before stage creation or any original move. These rows are audit, not approval proof. The journal must be in the ticket's pinned state directory. Migration preserves historical receipts and creates no invented agent associations. Bounded read-only receipts omit the nonce.

The shared operation coordinator now serializes native work and headless scans under the same OS lease. Protection and note writes acquire the same lease and fail while managed work is active. The prepared agent path now retains that exclusion and produces bounded results. Desktop request dispatch, external adapter wiring and full elevated/Shell acceptance through the agent path remain pending. CLI/MCP execution stays disabled.

The headless service retains its canonical state-directory coordinator for its entire lifetime, including clones and cached queries. All registry, snapshot, job and plan paths derive from it. Windows directory pins request directory-list access without enumerating or reading file content; attribute-only handles did not prevent renaming in the regression fixture. Leaf directories are reopened through the original handle before their canonical name is retained. The [CreateFile documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) explains the special sharing semantics for attribute access. Regular-file metadata handles retain attribute-only access.

Owned-fixture tests cover forged database approval, wrong hashes, expiry, restart, changed files, changed hard-link count, principal isolation, rotation, limits, rejection, protected selections, changed protection policy and eight competing requests. These tests issue and consume execution tickets without cleaning any user data. They do not establish native UI acceptance or actual approved recycling through CLI/MCP.

An additional service fixture uses persisted snapshot evidence and the separate desktop facade to prove review, rejection, session closure and renewal, unavailable revoked connections and rejection of legacy or changed evidence. Real CLI and MCP fixtures cannot grant approval or modify source files. The UI retains a named, focusable overflow region for keyboard access to the full file selection, following [MDN's overflow accessibility guidance](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/overflow#accessibility); interaction and scaling acceptance remain manual.
