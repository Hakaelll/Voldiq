# Developer storage

Developer analysis classifies measured directories from the current index. It uses the same logical size, allocation and incomplete-coverage evidence as Explorer. Nested candidates belong to the outer directory so totals do not count a subtree twice. Pages contain at most 100 directories. Analysis does not execute tools or remove files.

## Project artifacts

Cargo targets require a sibling `Cargo.toml`; Node.js dependencies and build output require `package.json`. CMake builds require `CMakeLists.txt`. Gradle project caches require a Gradle build or settings file. .NET build directories require a C# or F# project. Python bytecode directories use their conventional `__pycache__` name.

Manifest entries must be complete. The Cleanup view's Project temporary files rule reuses these classifications for explicitly selected `.tmp`/`.temp` files aged at least seven days inside Build scopes. It excludes recognized dependency and configured-cache ancestry, preserving nested exclusions before Developer totals are deduplicated. This does not authorize removing entire artifact directories or cache trees. See [project temporary-file review](CLEANUP.md#project-temporary-files).

## Global tool locations

Global-cache analysis resolves the current Windows profile and local-data directory through Tauri's native path resolver. An absolute `CARGO_HOME` overrides the profile's `.cargo` location. Only its `registry` and `git` directories are classified as cache; installed tools, configuration and credentials outside those directories are excluded. These locations are described in the [Cargo home documentation](https://doc.rust-lang.org/cargo/guide/cargo-home.html).

An absolute `NPM_CONFIG_CACHE` has priority. Otherwise npm discovery reads the profile's `.npmrc`, or an absolute `NPM_CONFIG_USERCONFIG` override, followed by an explicitly supplied absolute `NPM_CONFIG_GLOBALCONFIG` when the user file has no cache setting. With no recognized setting, it uses Windows `%LocalAppData%\npm-cache`. This follows the supported part of [npm's configuration order](https://docs.npmjs.com/cli/v11/using-npm/config/) and [npmrc format](https://docs.npmjs.com/cli/v11/configuring-npm/npmrc/).

Reads are limited to 65,536 UTF-8 bytes and extract only the top-level scalar `cache` setting. Comments, repeated scalar settings, quoted paths, escaped comment characters, `${VARIABLE}` substitutions, optional `${VARIABLE?}` substitutions and `~/` home paths are supported. Escaped variable expressions retain their literal path according to [npm's backslash-parity rule](https://github.com/npm/cli/blob/latest/workspaces/config/lib/env-replace.js). Windows file opens reject reparse/cloud-placeholder leaves before content reads. Configuration contents and credentials are never returned through IPC or persisted.

Unreadable, oversized or uninterpretable files and relative, array-valued or unresolved paths omit npm classification instead of measuring another cache. Project/CLI/builtin settings, inferred global-config locations and user-file `globalconfig` redirects remain uninspected. Some quoted forms accepted by npm's permissive INI parser are conservatively omitted. No npm command runs, and these known locations do not prove the active cache for every project.

Locations must exist and resolve to indexed directories. The query uses their recorded sizes rather than scanning again. A scan or query rooted inside a cache reports only that measured subtree. New snapshots record the matching directory IDs, tool and category at capture time. Historical queries use those records and ignore current environment/configuration locations. Older captures retain project classifications from their recorded rows without inventing global-cache labels.

Snapshot schema version 4 introduced at most 1,024 matching cache roots per capture, in the same transaction as the indexed entries. Current schema version 5 also stores persistent duplicate hashes and migrates versions 0–4 transactionally; older application binaries cannot reopen a version 5 database. Cache metadata points to existing snapshot paths; it does not copy outside paths, configuration contents or credentials. Scoped scans retain only their measured root or descendants. Overlapping roots use the same most-specific matching location and dependency tie-break as the live query. Capture cancellation rolls back metadata with the rest of the capture; capture deletion removes its metadata. Loading validates directory membership and the supported tool/category values in the same read transaction as the index. NTFS replay discards historical cache evidence before publishing a live result.

The [snapshot cache verification](../benchmarks/snapshot-cache-verification-2026-10-15.json) records the source gate for this change. Four disposable snapshot fixtures verify restart, changed current locations, unrelated namesakes, scoped dependency precedence, unchanged comparison totals, deletion, cancellation, rejected malformed metadata and migration from version 3. The existing migration fixtures also exercise versions 1 and 2. Native populated interaction remains a separate manual check.

The Windows resolver also recognizes these locations and their absolute environment overrides:

| Tool | Default location | Override | Category |
|---|---|---|---|
| pnpm store | Versioned directories beneath `%LocalAppData%\pnpm\store` | `PNPM_CONFIG_STORE_DIR`, global YAML `storeDir`, then `PNPM_HOME\store` / `XDG_DATA_HOME\pnpm\store` | Cache / Dependencies |
| pnpm metadata | `%LocalAppData%\pnpm-cache` | `PNPM_CONFIG_CACHE_DIR`, global YAML `cacheDir`, then `XDG_CACHE_HOME\pnpm` | Cache |
| pip | `%LocalAppData%\pip\Cache` | `PIP_CACHE_DIR` | Cache |
| Gradle | `%UserProfile%\.gradle\caches` | `GRADLE_USER_HOME`, then `caches` | Cache |
| NuGet packages | `%UserProfile%\.nuget\packages` | `NUGET_PACKAGES` | Dependencies |
| NuGet HTTP | `%LocalAppData%\NuGet\v3-cache` | `NUGET_HTTP_CACHE_PATH` | Cache |
| NuGet plugins | `%LocalAppData%\NuGet\plugins-cache` | `NUGET_PLUGINS_CACHE_PATH` | Cache |

These locations follow [pip caching](https://pip.pypa.io/en/stable/topics/caching/) and its [cache-directory option](https://pip.pypa.io/en/stable/cli/pip/), [Gradle directory layout](https://docs.gradle.org/current/userguide/directory_layout.html) and [NuGet package/cache management](https://learn.microsoft.com/en-us/nuget/consume-packages/managing-the-global-packages-and-cache-folders). NuGet projects can use packages directly from the global packages directory, so it is labelled Dependencies. Gradle configuration, daemon files, installed JDKs and wrapper distributions are outside the selected `caches` directory.

Configuration files for tools other than the supported npm and pip sources, and command-line overrides, are not inspected. When configured locations overlap, a scoped query uses the most specific matching root. Coincident roots retain a dependency category when one is declared. A wider scan still aggregates nested locations into their outer candidate without counting bytes twice.

### pip configuration

The 2026-10-13 change passes the full workspace test suite and strict all-target Clippy. Twelve native developer resolver tests include five pip tests; source-only review verified the fixes for ignored sections and forged Windows folder variables. Populated native acceptance remains pending.

An absolute `PIP_CACHE_DIR` takes priority; a leading `~/` or `~\` resolves beneath the profile. Otherwise discovery combines `pip.ini` in the native Windows ProgramData folder, the legacy profile `pip` folder, the native RoamingAppData `pip` folder, the `VIRTUAL_ENV` folder when provided, and an absolute `PIP_CONFIG_FILE`. An existing explicit file suppresses the user files. The exact Windows null-device value `nul` disables configuration reads. This follows the supported Windows [pip loading order](https://pip.pypa.io/en/stable/topics/configuration/).

Later files replace earlier `cache-dir` values in the same section. Exact `global` and recognized pip command sections contribute a union of known cache locations; `DEFAULT` values inherit into those sections. Unknown sections and uppercase variants such as `GLOBAL` do not classify directories. This union can include different command caches and does not identify one active cache for every interpreter or invocation. `VIRTUAL_ENV` is an approximation of an interpreter's `sys.prefix`; Python installation roots, isolated execution and platformdirs `WIN_PD_OVERRIDE_*` settings remain uninspected.

npm and pip share a read-only UTF-8 reader bounded to 65,536 bytes per file. Windows opens reject reparse/cloud-placeholder leaves before content reads. Duplicate sections/options, malformed or multiline cache values, oversized/unreadable files, non-UTF-8 encodings and unresolved relative paths omit pip classification. Literal `#`, `;` and variable expressions in values are preserved; pip configuration values are not interpreted as npm substitutions. Configuration contents and credentials are not returned or persisted. Only existing indexed cache directories contribute measured sizes, and no pip command runs.

pnpm discovery follows its documented [store settings](https://pnpm.io/settings/store), [metadata cache setting](https://pnpm.io/settings/other#cachedir) and [global YAML configuration location](https://pnpm.io/cli/config). It reads `$XDG_CONFIG_HOME/pnpm/config.yaml` when configured, otherwise Windows `%LocalAppData%\pnpm\config\config.yaml`, with the documented home fallback when local app data is unavailable. The `storeDir` and `cacheDir` scalar settings select custom roots. Their respective `PNPM_CONFIG_STORE_DIR` and `PNPM_CONFIG_CACHE_DIR` environment overrides take precedence independently. With no configured store, `PNPM_HOME` and `XDG_DATA_HOME` precede the Windows default. Conventional locations recognize `v3`, `v10` and `v11`; explicit store settings use the existing v11 layout, appending `v11` unless the path already ends with it.

The YAML reader reuses the 65,536-byte UTF-8 file boundary and parses with `yaml-rust2`, capped at 4,096 events and 32 collection levels before materializing the document. It supports plain, quoted and block scalar paths, `${NAME}`, `${NAME-fallback}`, `${NAME:-fallback}` and leading `~/` home expansion. Paths must resolve to absolute locations. Aliases, root merges, duplicate keys, multiple documents, non-scalar path settings and unreadable or oversized files suppress fallback discovery. Explicit environment overrides remain independently usable. Directory environment variables must already be absolute and expanded; values containing percent signs are conservatively omitted. These rules follow the supported portions of pnpm's [global reader](https://github.com/pnpm/pnpm/blob/main/pnpm11/config/reader/src/getConfig/globalConfigYaml.ts), [directory lookup](https://github.com/pnpm/pnpm/blob/main/pnpm11/config/reader/src/dirs.ts) and [variable expansion](https://github.com/pnpm/pnpm/blob/main/pnpm11/config/env-replace/src/env-replace.ts). Configuration and credential contents are never returned or saved.

Each version's `files` and `index` directories are classified as Cache, alongside the configured/default metadata cache directory. `links` is classified separately as Dependencies because the [global virtual store](https://pnpm.io/global-virtual-store) can serve installed packages directly to projects. An aggregate cache row containing a configured dependency root is omitted from Developer totals so it cannot absorb that dependency category. Its complete cache evidence remains available to cleanup exclusions and snapshot capture; loose bookkeeping outside separately classified children is not counted in that ambiguous aggregate. Ordinary project markers inside a cache do not override that known cache location. Sibling binaries, configuration and unrelated files are excluded. Standalone bookkeeping files such as `index.db` remain visible in Explorer but are not included in these developer categories.

This is known-location analysis, not a claim that the discovered store is active for every project. Project YAML, legacy npmrc configuration, custom global virtual-store paths, stores selected for other disks, project-local store fallback and unrecognized future formats are not discovered automatically. No pnpm command is executed or configuration modified.

## Docker Engine analysis

The Docker panel performs only `GET /version` and a negotiated `GET /v1.x/system/df` on a local Windows named pipe. It defaults to `\\.\pipe\docker_engine` and accepts a local `npipe:////./pipe/NAME` or `npipe://./pipe/NAME`. TCP, SSH and remote pipes are rejected. The panel identifies the actual queried pipe. No Docker command, project script, service startup or folder deletion is performed.

### Local context discovery

Voldiq supports `DOCKER_HOST`, an explicit `DOCKER_CONTEXT`, or `currentContext` in the profile's `.docker/config.json`. An absolute drive path in `DOCKER_CONFIG` overrides that directory; UNC prefixes are rejected. Named contexts use `contexts/meta/<SHA-256 of name>/meta.json`, matching Docker's [context storage](https://raw.githubusercontent.com/docker/cli/master/cli/context/store/store.go). Only the matching name and `Endpoints.docker.Host` are used. An explicit default context uses `DOCKER_HOST` when present, otherwise the default pipe. Missing default configuration also uses that pipe; an invalid or missing selected context never falls back to another engine.

Simultaneous nondefault `DOCKER_CONTEXT` and `DOCKER_HOST` produce an explicit error. Docker's [documentation](https://docs.docker.com/reference/cli/docker/) and the inspected [CLI resolver](https://raw.githubusercontent.com/docker/cli/master/cli/command/cli.go) differ in their stated environment priority; Voldiq avoids choosing between them. Command-line flags, TLS material, credential helpers and remote transports are not supported.

Reads run off the IPC thread and share npm/pip's 65,536-byte UTF-8 reader. Reparse/cloud-placeholder leaves are rejected before content reads. The drive-path check is lexical: a mapped drive or ancestor junction may still redirect configuration reads to a remote location. Parent traversal is not an atomic namespace guarantee, unlike verified cleanup acquisition. Errors omit configuration contents and credentials. Configuration discovery and Engine requests share the existing 15-second response deadline; a blocked filesystem read may outlive that deadline on its worker. No configuration is modified or persisted.

The client supports Engine API 1.31–1.56, selecting the lower of the daemon's advertised version and 1.56 and checking its minimum version. Newer responses use `ImageUsage`, `ContainerUsage`, `VolumeUsage` and `BuildCacheUsage`. Legacy responses use `LayersSize` for images, `SizeRw` for containers, volume `UsageData.Size` and unshared build-cache records. Shared cache records remain in the item count. This follows the [current Engine schema](https://docs.docker.com/reference/api/engine/version/v1.56.yaml), [API changes](https://docs.docker.com/reference/api/engine/version-history/) and Docker's [legacy summary adapter](https://github.com/moby/moby/blob/master/client/system_disk_usage.go).

Missing measurements and the daemon's `-1` unknown-size sentinel remain Unknown. Invalid negative values, overflow and values beyond JavaScript's exact integer range are rejected. Categories are not added to a grand total: sizes may overlap and are Engine measurements, not Windows physical allocation or promised reclaimable bytes. Volumes are explicitly labelled persistent data.

The complete request sequence has a 15-second deadline. Headers, body and wire buffering are bounded; HTTP failures, truncation, unsupported transfer encoding and ambiguous framing return errors. The panel remains usable before a drive scan and has no management actions.

The [2026-10-15 verification](../benchmarks/docker-context-verification-2026-10-15.json) passed the six-stage source gate with this unit's working tree. Eight Docker tests cover stored/configured/default contexts, the exact hashed metadata location, invalid and conflicting settings, bounded reads, credentials omitted from errors, metadata mismatch, unavailable and remote endpoints, accounting and framing. A disposable context selects the actual Windows named pipe used by the GET fixture; its server checks the request method and path. npm/pip resolver tests also pass after sharing the reader. This does not establish acceptance with a running Docker Engine or the new command in the already-open native window.

On 2026-10-12, seven native tests passed, including four Docker tests covering current/legacy accounting, version and endpoint validation, HTTP framing, and an actual Windows named-pipe GET exchange plus silent-server timeout. ## Current Docker schema conformance

The [published API 1.56 schema](https://docs.docker.com/reference/api/engine/version/v1.56.yaml) and [Moby response type](https://github.com/moby/moby/blob/master/api/types/system/disk_usage.go) use singular `ImageUsage`, `ContainerUsage` and `VolumeUsage`, alongside `BuildCacheUsage`. The API version-history page describes plural names, so that changelog alone must not drive a decoder rename. The existing production decoder matches the published schema and remains unchanged.

The [2026-10-31 conformance record](../benchmarks/docker-schema-conformance-20261031.json) stores the downloaded schema hash and exact field references. The existing native boundary test now covers canonical summaries, transitional replies containing both summary and legacy fields, legacy accounting, known zero and unknown sizes. A temporary plural-field mutation failed against the canonical fixture and was discarded. No declared test was added.

The local CLI is installed and selects `desktop-linux`, but a read-only server-version request outside isolation failed because its local Engine pipe was absent. No engine or service was started. Running-Engine acceptance remains pending. The temporary schema download was removed after recording its hash.
