# Recycling transaction design

Status: implementation design, not an enabled executor. Cross-integrity admission/rollback and the separate Shell fixtures have passed. The combined admission-to-recycling transaction has not been verified.

## Implemented transport

[`windows::cleanup_channel`](../crates/voldiq-core/src/windows/cleanup_channel.rs) provides a one-connection local message pipe. Its protected DACL admits the current process user and SYSTEM, and the pipe rejects remote clients. Both endpoints compare Windows-reported pipe peer IDs with a live, retained process handle supplied by the caller. An unexpected peer closes the connection. The client requests identification-only security quality of service rather than the default impersonation level; see [Microsoft's named-pipe impersonation contract](https://learn.microsoft.com/en-us/windows/win32/ipc/impersonating-a-named-pipe-client).

Messages are bounded to 4 KiB. Empty/oversized outbound messages are rejected before I/O. Read/write/connect operations use overlapped I/O with a five-second wait. A timeout cancels and drains that specific operation before releasing its stack/buffer, then closes the channel. Cancellation completion itself is not promised to finish within five seconds. A failed receive cannot be resumed as a fresh protocol message.

The [initial normal-process observation](../benchmarks/cleanup-channel-2026-10-30.json) runs the actual module through [this executable fixture](../crates/voldiq-core/examples/cleanup_channel_probe.rs). It verifies a maximum-size message and reply, rejected outbound sizes, a rejected client process, a rejected server process, and cancellation/closure of an idle read. That run starts and reaps only its own child processes; it never elevates, relocates files or calls Shell. Reproduce the current extended fixture with `cargo run --release -p voldiq-core --example cleanup_channel_probe` on Windows. The retained eight-test suite is unchanged.

The admission session checks executable, user, role and elevation expectations before capability exchange. Cross-integrity source/parent transfer and admission/rollback passed the explicitly authorized UAC fixture below. Its PowerShell wrapper launched the helper; `Session::launch` itself has not been invoked. Malicious inbound frames and the complete admission-to-Shell transaction remain open. No desktop cleanup command exposes this channel.

### Source-handle transfer

`Channel::offer_source` borrows an existing file until the receiver acknowledges its native volume/file identity and granted access. `receive_source` pulls a duplicate from the authenticated peer process with `DUPLICATE_SAME_ACCESS`. It never treats a received numeric handle as locally owned authority, never closes the sender's original and never requests additional file rights. The channel retains its own process-handle reference for this exchange. Receiving requires `PROCESS_DUP_HANDLE` on that peer process. The stage design below avoids requiring the normal process to pull a directory handle from an elevated process.

The versioned fixed-size offer includes the source-process handle number, volume serial, full 128-bit file ID and granted-access mask. Both ends require disk files with delete/attribute-read rights and permit only optional data-read/synchronize rights. Writable/security-changing handles, directories, reparses and offline/recall-marked sources are rejected. The receiver independently queries the duplicate before acknowledging matching evidence. A malformed or failed transfer closes the channel and releases only receiver-owned resources. This transfers authority; it does not replace live-plan, metadata, content, ancestor or confirmation checks and does not authorize a filesystem mutation.

The [extended normal-process observation](../benchmarks/cleanup-source-transfer-2026-10-30.json) repeats the original transport checks and transfers one owned fixture. The receiving process cannot write through its duplicate. After the sender closes its original, renaming the source fails with sharing violation 32; after the receiver releases its copy, rename succeeds and the bytes remain unchanged. A crafted offer referring to a real read-only sender handle is rejected, the channel closes, and the sender can still read through its original handle. The fixture then removes its own files and directory. There is no elevation, protected staging or Shell call in that observation. Other malicious inbound forms and oversized inbound frames remain open; cross-integrity transfer passed the later identified UAC fixture.

### Stage-parent transfer

`offer_stage_parent` and `receive_stage_parent` use a distinct frame/acknowledgement kind for directory authority. Native validation requires directory-listing, attribute-read, create-subdirectory and delete-child rights already present on the sender's handle. Only optional read-control, read-extended-attribute, traverse and synchronize rights are accepted. The receiver verifies directory type, full volume/file identity and the unchanged granted-access mask after `DUPLICATE_SAME_ACCESS`. This does not permit replacing a source-file message with a directory message or using a listing-only parent as evidence of ordinary create/remove authority.

The [stage-parent observation](../benchmarks/cleanup-stage-parent-transfer-2026-10-30.json) repeats the earlier channel/source checks and transfers a real parent directory between normal processes. The receiver independently acquires the existing protected stage through the duplicated parent and checks its expected identity and permissions. After the sender closes both creator handles, parent and stage renames still fail with sharing violation 32. The parent can be renamed after the receiver releases both handles. A parent lacking create/remove rights and an attempt to offer the directory as a source file are rejected before transmission. Owned directories are then removed. This verifies normal-process authority transfer and cross-process namespace pinning, not elevated admission or the complete cleanup transaction.

### Admission and explicit return primitives

[`StagePin::admit`](../crates/voldiq-core/src/windows/cleanup_stage/admission.rs) accepts an already verified source handle and a validated single filename. It checks source access/type/attributes, rejects read-only sources and a populated stage, and requires matching native volume-GUID roots. It calls `NtSetInformationFile(FileRenameInformation)` with the SDK layout, the retained stage directory as `RootDirectory` and `ReplaceIfExists = false`. It has no source-path reopen, cross-volume copy, permanent-delete or attribute-override fallback. The directory is hidden from creation time, and its pin retains a reference to its parent.

`StageEntry` preserves supported Unicode filenames while rejecting separators, streams, controls, trailing dots/spaces, oversized components and reserved Windows device names. Use one protected stage per source in the initial executor so Shell retains a meaningful original filename. `return_to_parent` is a separate rollback primitive: it requires exactly the expected staged entry, checks that entry against the retained source's full native identity, and moves that source to the stage's captured parent without replacing a destination. It does not restore a Recycle Bin item. The executor must place the stage under the reviewed source's original parent; returning to an arbitrary staging location would not restore the original location.

The [normal-token admission observation](../benchmarks/stage-admission-normal-2026-10-31.json) records native admission rejection with access denied 5, followed by unchanged source identity/content and an absent destination entry. It also checks filename validation and repeats cross-process transport, source/parent authority and namespace guards. The later UAC receipt below proves elevated admission, ordinary rollback and collision preservation for its identified source/executable version. Successful populated-stage replay rejection and the complete admission-to-Shell transaction remain open. Relocation intent must be durable before either mutation primitive is called; an error is not proof that retry is safe.

### Parent authority and empty-stage cleanup

`VerifiedFile::stage_parent` obtains preparation authority from the retained parent object, without reopening a source pathname. It checks the planned source stamp and parent identity, requests directory creation/removal plus ordinary file-creation rights for rollback preflight, then duplicates only the bounded transferable parent mask. The initial broader handle closes before return. The shared mask excludes file creation from the transferred capability.

The parent uses `NtCreateFile(FILE_OPEN)` with an empty name relative to the held directory. `ReOpenFile` returned access denied for the retained directory on this host; the native relative open succeeds and preserves full identity. Both calls are ordinary-token acquisition attempts, not administrator workarounds.

`StagePin::remove_empty` releases its old read pin, opens only the recorded child relative to its captured parent, checks the full expected identity and exact protected policy, and requires an empty directory before setting disposition on that same handle. It never recursively deletes or follows a replacement. [The ordinary receipt](../benchmarks/stage-admission-ordinary-20261031-004056-526.json) proves parent acquisition/narrowing and empty-stage removal. Supplying a different directory containing an owned marker is rejected without altering that marker. The six retained core tests and all-target Clippy passed. [The early parent-probe residue](../benchmarks/parent-capability-probe-cleanup-20261031-003923.json) contained only its exact four-byte fixture and was cleaned through its retained handle, without recursive removal.

### Source acquisition and handle lifetime

Desktop code now has `VerifiedFile::offer_source`, which rechecks the planned stamp before lending the internally acquired source. Its constructor uses the cleanup engine's fixed no-follow/no-recall, synchronous open flags and never requests delete-on-close. The extended channel fixture scans its real disposable source, builds a manual plan, verifies it, and transfers that metadata-only source through this method. The receiver remains unable to read file data.

Observable pending deletion and non-synchronous I/O are rejected by the shared source-access check. They do not prove the complete acquisition history. The [owned zero-byte flag-visibility observation](../benchmarks/source-open-flag-visibility-2026-10-31.json) explicitly requests delete-on-close, yet Windows returns mode 32 and `DeletePending = false`; closing the original handle still removes the fixture. An earlier attempted rejection assertion therefore failed, correctly exposing an invalid assumption. The implementation relies on the verified constructor for that lifetime invariant rather than claiming that metadata establishes it. Low-level `Channel::offer_source(File)` requires trusted acquisition; it is not an alternative frontend entry point. No code clears a caller's deletion flags.

### Protected namespace pins

[`windows::cleanup_stage`](../crates/voldiq-core/src/windows/cleanup_stage.rs) creates an empty protected directory relative to an already opened parent. The backend chooses a validated `StageName` before creation so it can record that name before mutation. Creation uses `FILE_CREATE`, never an open-existing fallback. The protected descriptor applies from the first instant: enabled Administrators have full access; the current user and OWNER RIGHTS have only read/list/traverse access. The explicit owner-rights entry suppresses implicit owner permission to rewrite the DACL.

`StagePin::acquire` independently opens an existing stage through its parent handle, checks its full native identity and compares the actual owner/protected DACL with the expected policy. Both creation and acquisition retain directory-listing handles without delete sharing. Invalid names, collisions, wrong identities, reparses and unexpected permissions fail closed. The implementation limits stages to fixed local NTFS volumes with persistent ACLs and a stable volume-GUID path. A failure after native creation can leave the already named empty directory for explicit reconciliation; no source has been relocated.

The [normal-token pin observation](../benchmarks/protected-stage-pin-2026-10-30.json) exercises [the actual module](../crates/voldiq-core/examples/protected_stage_probe.rs). A second read-only pin preserves the directory name after the creator pin closes. Child creation and rewriting the unchanged DACL fail with access denied; rename fails while pinned and succeeds after release, preserving identity. Wrong identities, duplicate creation and an ordinary directory with incorrect permissions are rejected. The fixture removes its own empty directories. The same record reruns the channel/source fixture after sharing the Windows security-descriptor implementation.

The initial directory-create attempt combined directory creation with `FILE_OPEN_NO_RECALL` and returned `STATUS_INVALID_PARAMETER` on this host. Creation now uses no-follow directory creation, while acquisition uses a type-neutral no-follow/no-recall open followed by directory validation. No fallback follows reparses or relaxes the DACL. See the [native create options](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile).

## Existing execution path

`Plan` owns the reviewed selection, source stamps, ancestor identities and retained duplicate copies. `consume_plan` in the desktop adapter checks the live index and consumes confirmation once. The permanent executor retains verified handles, calls `Journal::prepare_permanent`, commits `start_item` before disposition, and records the result afterward. Journal schema 3 preserves those permanent-operation tables and extends the separate admission ledger with recycling/restoration evidence. Reopening it marks interrupted in-flight results unknown. The full desktop transaction still needs to use this path without weakening its confirmations or treating an unknown result as success.

The original requirements allow elevation for one explained operation and prohibit elevating the whole application. They require race protection, partial-result reporting and a distinction between recycling and permanent deletion. They do not authorize silently substituting permanent deletion when recycling fails.

## Chosen boundary

### Admission helper entry

`cleanup::helper` is now the shared controller/helper protocol. The desktop checks `--cleanup-helper` before constructing Tauri, creating its window or opening application databases. This entry requires an elevated token and a same-user, same-image ordinary controller. The bounded loop accepts at most 500 sequenced admission requests containing only source/parent capabilities, a stage name/identity and a validated filename. It has no source-path reopen, recycling, permanent deletion or service command.

The ordinary-creator alternative was tested before expanding this boundary. A new stage's creator can retain ADD_FILE and broader directory rights even while later ADD_FILE/WRITE_DAC opens are denied. Nevertheless, native rename admission into its protected DACL still returns `STATUS_ACCESS_DENIED`, including when FILE_ALL_ACCESS was requested. Both probes preserved the source's original identity and four bytes, then cleaned only their own objects. The [minimal grant](../benchmarks/creator-stage-authority-20261031-001621.json) and [broader grant](../benchmarks/creator-stage-authority-20261031-002229.json) receipts include their exact scripts. Creation-handle authority therefore does not remove the demonstrated need for the chosen admission boundary on this host.

The controller pins the selected executable before `ShellExecuteExW(runas)`, retains the actual returned process handle and authenticates the channel against it. Consent failure occurs before source capabilities are sent. A successful helper response follows closure of all per-item source and directory handles, including failed admissions. Completion requires the protocol's release acknowledgement and verified process exit. Communication errors close the session; no helper is killed, restarted or reused after an uncertain result. The elevated launch path remains unverified and is not enabled in the cleanup UI.

The native fixture now uses this module instead of maintaining a separate admission implementation. [The ordinary protocol receipt](../benchmarks/stage-admission-ordinary-20261031-000852-493.json) confirms capability transfer, native access denial, durable results and reacquisition of DELETE authority while the helper is still alive. This checks actual release of its strict source duplicate, not just a reply flag. Cross-integrity admission/rollback subsequently passed the UAC fixture. The elevated desktop entry and `Session::launch` runtime remain unverified.

`cargo check --offline --release -p voldiq` passed for the native entry, and `cargo test --offline --release -p voldiq-core` passed the six retained core tests. [The shared CLI-entry receipt](../benchmarks/helper-ordinary-entry-20261031-001142.json) confirms that an ordinary token is rejected for the production helper role before any pipe connection. This executes the shared entry in the core example, not a rebuilt desktop executable. No additional declared test was added.

### Rust recycling boundary

`cleanup::recycle` now contains the Rust primitive. `VerifiedFile::prepare_recycling` accepts only a source already verified inside a retained protected stage. It validates the reviewed identity, size and modification time, obtains a read content guard with `ReOpenFile`, and checks its full native identity before releasing the strict leaf handle. Ancestor pins and the stage borrow remain alive. `StagedSource::recycle` validates the native staged entry and Shell-resolved objects, then commits a journal intent bound to the retained source and stage identities before calling `ITransferSource::RecycleItem` once. It checks the returned bin item's full identity against the retained guard and records its exact native locator. A `RecycledItem` borrows the content guard and STA apartment. If result recording fails after verified recycling, it returns the native evidence with `recorded() == false` and a journal error; the executor must stop the batch. It does not implement native restoration yet.

`ShellApartment::check_stage` checks the actual transfer binding and recycling destination before privileged admission. Shell rejected a volume-GUID parsing path with `E_INVALIDARG` on this host. Native staging still uses volume-GUID addressing. Shell paths instead require a fixed physical drive with matching current/global DOS-device targets, reject substituted/local aliases, and compare the resolved directory's native identity against the retained pin. The Shell-resolved parent is checked again before constructing its relative source item. Unsupported path representations fail before admission; there is no general path fallback.

The ordinary observation [stage-admission-ordinary-20261030-235756-156.json](../benchmarks/stage-admission-ordinary-20261030-235756-156.json) proves that the actual Rust STA/binding works on the protected stage and that an unadmitted source is rejected. The two earlier path failures occurred before helper admission. Their retained files and directories were reconciled against journal identities and cleaned through owned file handles; [the reconciliation receipt](../benchmarks/stage-shell-path-reconciliation-20261030-235615.json) includes the exact bounded script. Successful Rust recycling from an admitted stage remains unverified pending the combined native gate. No desktop command enables this primitive yet.

The helper protocol must confirm closure of its duplicated strict source handles before Shell execution; retaining those handles intentionally prevents Shell from moving the source. The shared helper now closes them before each response, and the ordinary fixture verifies that release. The fixture still does not exercise recycling.

On this host, `ReOpenFile` rejects `OPEN_NO_RECALL` with native error 87 even though the documented flag table includes it. [The bounded inspection](../benchmarks/reopen-no-recall-20261031-000804.json) compares three original access masks and confirms successful controls with `OPEN_REPARSE_POINT` alone. The Rust content handoff and release check now use the successful flags. They retain local-file, online/non-reparse metadata checks and identity validation. Initial path opens still use no-recall flags. [The retained fixture from that failure](../benchmarks/helper-release-reconciliation-20261031-000953.json) was reconciled against its `unmoved` journal result and cleaned only after source, parent and stage identities and original bytes matched.

### Native recycling choice

Use the Shell's dedicated `ITransferSource::RecycleItem` for the recycling primitive. Its contract returns the recycled item in the supplied recycling location and is separate from `RemoveItem`. Acquire it from the captured source folder through `IShellItem::BindToHandler(BHID_Transfer)`, and use the Windows Recycle Bin known-folder item as the destination. Do not call `RemoveItem`, retry with permanent deletion, or treat a successful HRESULT without a returned item and verified native identity as completed recycling. See [RecycleItem](https://learn.microsoft.com/windows/win32/api/shobjidl_core/nf-shobjidl_core-itransfersource-recycleitem) and [BHID_Transfer](https://learn.microsoft.com/windows/win32/api/shobjidl_core/nf-shobjidl_core-ishellitem-bindtohandler).

The owned native fixture `benchmarks/shell-content-guard-probe.cpp --direct` has demonstrated this primitive with baseline and retained-content-guard sources. Both returned items matched their original 128-bit identities and restored four original bytes through the previously checked Shell move flow. The guarded case refused writes with native error 32. This avoids implementing recycling through the general delete operation; it does not prove unavailable-bin behavior or the protected-stage/elevated-helper integration. A later direct-transfer restoration comparison is documented below; no Rust restoration primitive is enabled yet.

The current-source observation is [shell-direct-recycle-20261030-234603-678.json](../benchmarks/shell-direct-recycle-20261030-234603-678.json), which also confirms the original general-delete fixture mode. Both modes cleaned their own files and empty fixture directories. The fixture now exits successfully only when both baseline and guarded sources were actually recycled, restored and cleaned; successful cleanup alone is insufficient.

Keep review, journal ownership, protected-stage creation/pinning, Shell calls and restoration in the ordinary desktop process. Use one short-lived elevated helper per explicitly confirmed batch only to admit the already verified files into those stages. No resident service, scheduled task or permanent administrator setting is installed.

The helper must receive source authority through duplicated handles acquired by the ordinary process. It must not accept a pathname and reopen it with administrator permissions. `DuplicateHandle` retains the same underlying object; its numeric value belongs to the receiving process and is never durable recovery data. See [Microsoft's handle contract](https://learn.microsoft.com/windows/win32/api/handleapi/nf-handleapi-duplicatehandle).

Create each staging directory with its protected security descriptor from the first instant. Normal callers may read/list/traverse but may not add children, change security or install reparse metadata. Administrators retain admission authority. The normal process already owns the read-only pin; no administrator security-modification handle crosses back into it. Keep the directory pinned against deletion and rename throughout handoff and Shell execution. A writable parent must not permit replacing the directory through parent delete-child authority.

Use stable same-volume addressing and independently verify volume, directory and source identities. Start with supported local NTFS volumes. Reject unsupported permissions, filesystem behavior, paths or identity representations before relocation. Do not infer a successful protected namespace from a random directory name. New-object security must be explicit rather than inherited from a writable parent. See [security descriptors for new objects](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptors-for-new-objects).

## Ownership and sequence

1. Consume the confirmed live plan and acquire the existing strict source/ancestor guards. Keep duplicate retained-copy authority alive for the batch.
2. Commit original paths, native identities, stamps and intended stage locations to the journal before any source relocation. Create/pin each stage as the ordinary user and commit its actual identity. Require ordinary authority to create and remove empty directories beneath the stage parent, and the same volume as the source. If any check or commit fails, do not move files or start Shell operations.
3. Launch the one-use helper through Windows consent. Authenticate both IPC endpoints, constrain the protocol to this batch, reject remote clients, and bind the actual peer process and user. A pipe name or caller-supplied PID alone is not authentication. Declined consent leaves sources unchanged.
4. The helper authenticates the source and stage-parent capabilities, validates the existing stage's identity/policy and waits for journal readiness. It may not create a directory with administrator permissions or reopen a source by pathname. Only then may it enroll a source through its duplicated handle. The ordinary process retains the stage pin and strict source guard across this step.
5. In the ordinary process after relocation, verify the staged object and acquire the read content guard through `ReOpenFile` on the retained source object, before releasing the strict leaf guard. The elevated helper must not introduce read rights that the ordinary caller could not acquire. Keep ancestors, stage and content pinned. Account for metadata changes caused by the application's own rename; do not waive identity or content validation because a pathname matches.
6. Commit recycling intent. On an STA worker, queue only the verified staged item with recycle flags. Require the per-item callback and an actual returned Recycle Bin item. A successful queue or aggregate HRESULT is insufficient. Never retry as permanent deletion.
7. Persist the returned bin-item locator, native identity and original-location mapping before reporting success. If this write fails, stop the batch and retain an unresolved result. Do not retry the native action.
8. Release per-item guards only after recording the outcome. The ordinary process removes only verified empty staging directories using its existing parent authority. No actor recursively deletes stage contents. Refresh the index after the batch; moving to the bin does not itself establish recovered allocation.

Cancellation stops admitting new files. An admitted file needs a recorded outcome or a verified move back; it must not disappear from activity because the user canceled. Helper exit, IPC loss, journal failure and application shutdown follow the same rule.

## Journal and recovery

The implemented schema-1-to-2 migration runs inside the existing exclusive transaction. Admission records store the exact canonical original path, source volume and 128-bit file identity, parent identity, original metadata stamp, intended stage name and actual stage identity. A unique live-source index prevents duplicate enrollment, including unresolved outcomes. The executable fixture commits intent before stage creation, stage identity before admission, and return intent before rollback. It reopens the database and checks the terminal evidence. `prepared` becomes `cancelled` on restart; stage-ready, relocating, staged and returning records become `unknown`. Old session tokens cannot advance them. Listing recovery evidence performs no filesystem operation.

`benchmarks/stage-admission-ordinary-20261030-234145-788.json` records the ordinary helper run with this ledger integrated, including the successful close/reopen check and current executable/source hashes. The six retained core tests passed after this change. No additional declared test was added.

Schema 3 adds exact UTF-16 bin and explicit restoration-destination paths, plus recycling, recycled, restoring and restored states. The version-2 table migration preserves old rows, identities and the AUTOINCREMENT high-water mark in the same exclusive transaction. A completed recycled receipt remains a historical result on restart; interrupted recycling/restoration becomes unknown while retaining any recorded locator and destination. Journal methods record evidence only and never reopen or mutate files.

The retained journal regression now covers schema-1 permanent history, schema-2 admission history, interruption at each operation phase, wrong source identity, repeated transitions, failed receipt writes, stale-session rejection and a native locator with an unpaired UTF-16 surrogate. It verifies the locator is preserved exactly and that original fixture files are unchanged. These are ledger assertions, not native recycling/restoration claims. All six retained core tests and all-target Clippy passed. [The schema-3 ordinary receipt](../benchmarks/stage-admission-ordinary-20261031-002251-035.json) confirms the existing helper flow and terminal evidence survive restart. The desktop executor does not yet use the recycling transaction. Combined Rust recycling and native restoration remain behind their proof gates.

Extend the existing database with an atomic, versioned migration that preserves permanent-operation history. Model recycling separately from permanent removal. Persist exact original and stage names, volume identity, file identity, stage-directory identity and a recoverable Shell locator. Store no raw process handles, lossy path conversions or assumed-success flags.

| Durable state | Next permitted action |
|---|---|
| Prepared source | Validate and stage, or cancel without touching it |
| Protected stage recorded | Admit only after the ordinary process owns its pin |
| Relocation in flight | Reconcile identities at original/stage locations; do not blindly retry |
| Staged | Verify and recycle, or explicitly restore the verified original |
| Recycling in flight | Reconcile stage and recorded Shell evidence; otherwise remain unknown |
| Recycled with locator | Offer restoration of this recorded item |
| Restoration in flight | Reconcile identities before reporting a result or another attempt |
| Restored | Report its verified destination and refresh the index |

Unknown outcomes stay unknown when evidence is missing or contradictory. Startup performs read-only reconciliation; it does not automatically move or delete anything. Reacquire and verify every recovery object before an explicitly requested action. A path reoccupied by another file must remain untouched.

Shell records the staging location as the deletion origin, so the application must retain the actual original-location mapping. Restoration acts on the returned bin item and this mapping, not the session-wide Undo stack. Check destination authority, refuse overwrite, and offer a separately confirmed destination when the original is unavailable. A restored stage path is not the user's original location.

### Batch executor

`cleanup::recycle::batch` consumes a confirmed plan on a dedicated STA worker. It verifies duplicate keepers, captures ordinary parent authority, records each intent, creates and checks protected stages, and checks Shell binding before requesting a helper. All admissions finish and the authenticated helper session closes before recycling or ordinary returns begin. Cancellation returns known staged sources without overwriting occupied names. Uncertain admissions or native recycling results remain unresolved and stop further recycling.

Preparation errors retain the original strict source guard for return. A failure before the native recycling call can reacquire strict authority from the retained content guard before releasing that guard. Once the native call has been attempted, the executor does not retry or assume the source stayed in the stage. Results include the read-only journal identifier and, after verified recycling, the exact native UTF-16 bin locator even if recording that receipt fails.

The [ordinary batch receipt](../benchmarks/stage-admission-ordinary-20261031-091442-183.json) exercises production batch preparation and execution with an authenticated ordinary helper. The fixture extends the existing native example and adds no declared tests.

### Restoration control and collision behavior

The SDK fixture now has `--direct-move` and `--undelete` modes. The former binds the returned item's parent transfer handler and calls `ITransferSource::MoveItem` with `TSF_FAIL_EXIST`. It first creates an owned replacement at the original name, verifies that the native collision leaves both identities and contents unchanged, removes only that replacement by its retained handle, and restores the original. It checks the returned destination, full native identity and original four bytes. The Windows control invokes `undelete` on only the exact owned item selected from the bin namespace, with its original destination empty. See Microsoft's [MoveItem](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-itransfersource-moveitem), [transfer flags](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/ne-shobjidl_core-_transfer_source_flags) and [bin command example](https://devblogs.microsoft.com/oldnewthing/20110901-00/?p=9753/).

The [completed comparison](../benchmarks/shell-restore-control-comparison-20261031-093059-363.json) passed both baseline and retained-read-guard cases for both modes. Direct moves returned the same original identity and bytes, refused the occupied name with `0x800700b7`, and needed no recovery fallback. The guarded case still rejected writes with sharing violation 32. Each fixture removed its own restored files, exact identity-matched metadata and empty directory.

An initially added requirement that the physical `$I` metadata disappear immediately was incorrect. The native Windows `undelete` control also leaves that metadata on this host after successful restoration. Earlier records with `restored = true` and a nonzero exit reflect that additional criterion. The first data-object experiment instead returned an unexpected effect and left restoration unverified, even though final cleanup found and removed the owned source by its original identity. The [rerunnable census](../benchmarks/restore-metadata-census.ps1) includes the Windows control. The corrected gate checks actual restoration, original identity/content, absent bin payload and collision preservation. Production behavior must not depend on undocumented metadata deletion timing.

The earliest direct-move experiment and the first data-object experiment left only their own small metadata records after payload cleanup. Their bounded [two-item reconciliation](../benchmarks/direct-move-metadata-reconciliation-20261031-092022.json) and [single-item reconciliation](../benchmarks/direct-move-metadata-reconciliation-20261031-092431.json) match exact GUID original paths, four-byte size, absent source/payload and retained native identities before removing those metadata files. No other bin item was modified. Later fixtures capture their metadata identities and clean these owned artifacts themselves.

These observations cover disposable files on this host. They do not prove source-namespace substitution resistance during restoration, recovery after interruption, the protected-stage transaction or the desktop command. Those requirements remain open before integration.
